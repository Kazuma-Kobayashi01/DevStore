# v3 数据模型与能力边界

日期：2026-10-29。状态：**设计草案；第 7 节待决问题已由用户逐条决定**。依据：[单卷方案 v3](../reports/单卷独立环境挂载方案-v3.md)、[Miniconda 实验](../reports/Miniconda单卷实验结果-20261029.md)。本文只定义数据与行为约定，不含 Swift 实现；示例用 JSON 表达结构，最终字段名可在实现时调整。

## 1. 目标与非目标

目标：让 CLI、MCP Server 与 SwiftUI 共用一套核心模型，能够回答"这个环境是谁、在哪、能否安全挂载、上次验证到什么程度、这次操作会改什么、谁批准了"。

非目标：进程隔离、跨主机并发读写、自动迁移现有安装、秘密管理。初版只实现已验证的 Miniconda 适配器；其他 kind 只保留模型位置。

## 2. 三处存放位置

数据分三层，任何一层丢失都应能从另外两层重建或至少安全拒绝操作。

| 层 | 位置 | 内容 | 丢失后果 |
|---|---|---|---|
| 卷内清单 | `<mount>/.devstore/` | 环境身份、适配器及版本、路径映射、数据分类、组件清单、最近验证摘要 | 环境不可自描述；只能按映像旁注重建 |
| 存储库 | `<store>/`（内置盘或外置 SSD） | `store.json`、每个映像的旁注 `image.json`、租约、检查点及其内容清单 | 映像仍可挂载，但需重新登记 |
| 主机登记 | `~/Library/Application Support/DevStore/` | 已知存储库、挂载槽占用、事务日志、授权记录、本机宿主依赖探测结果 | 可通过扫描存储库重建；未完成事务需人工确认 |

原则：**主机登记只是索引和日志，不是唯一真相**。环境的定义随卷走，映像的定位随存储库走。

格式：三层都用 JSON。状态类文件（`registry.json`、`store.json`、`image.json`、卷内清单）整体写临时文件后原子替换；事务日志 `journal.jsonl` 与授权记录 `grants.jsonl` 为只追加的 JSON Lines。数据量小，优先可读、可手修，不引入 SQLite。每个文件带 `schemaVersion`。

存储库布局（沿用 v3）：

```
<store>/
  store.json
  environments/<kind>/<environment-id>/
    environment.sparsebundle
    image.json            # 映像旁注，无需挂载即可读取
    lease.json            # 仅在被某主机挂载期间存在
  checkpoints/<environment-id>/
    <checkpoint-id>.dmg
    <checkpoint-id>.json  # 元数据 + 内容清单摘要
    <checkpoint-id>.manifest.json.zst  # 逐文件清单（可选，较大）
```

## 3. 核心实体

```
Store 1─* Image *─1 Environment *─1 Adapter(kind)
Environment 1─* Checkpoint
Host 1─* MountSlot(kind) 0..1─ Image
Operation(Plan → Grant → Transaction) ─ 引用 Environment / Image / Checkpoint
VerificationRun ─ 引用 Image 或 Checkpoint、Adapter 验证套件版本
```

### 3.1 Environment（逻辑环境）

一个逻辑环境 = 一个 kind 下用户命名的实例，例如"本机 Miniconda 主环境"。它可以先后对应多个映像（恢复、转移都会产生新映像），这些映像可以分属不同存储库，但**同一时刻只有一个映像是该环境的 `active` 映像**。同一 kind 可以有多个环境同时挂载，各占一个槽位（见 3.7）。

| 字段 | 说明 |
|---|---|
| `environmentId` | 随机 UUID，创建时生成，写入卷内清单；跨复制保持 |
| `kind` | `miniconda`、`go`、`dotnet`…… |
| `slot` | 槽位名，决定挂载路径 `~/.local/dev/<kind>/<slot>`；每 kind 第一个环境默认 `current`。同主机同 kind 内唯一；创建后视为固定（见 3.7） |
| `displayName` | 用户可改 |
| `adapter` | `{ id, version }`，指适配器声明，不是被管理工具的版本 |
| `activeImageId` | 当前活动映像 |
| `origin` | 来源：`imported`（自哪个原安装路径、何时）/`created`（官方二进制包 URL 与摘要）/`restored`（自哪个检查点） |
| `secretsPolicy` | `none`（默认）/`userManaged`；不自动导入令牌，如 Miniconda 实验未复制 `~/.conda` 登录令牌 |

### 3.2 Image（活动映像）

| 字段 | 说明 |
|---|---|
| `imageId` | 随机 UUID，**每次复制、恢复、转移都生成新值**并写入 `image.json` |
| `environmentId` | 所属逻辑环境 |
| `storeId` + 相对路径 | 定位；不存绝对路径 |
| `format` | `UDSB`（可写 sparse bundle） |
| `virtualCapacityBytes` | 如 8 GiB |
| `volumeUUID` | APFS 卷 UUID，**只作辅助核对**；复制映像可能保留同一 UUID |
| `role` | `active` / `standby`（恢复出来但尚未切换）/ `retired`（已被替换，保留待用户删除） |
| `lineage` | `{ parentImageId?, fromCheckpointId?, reason }` |
| `fixedMountPath` | 创建时写死的挂载路径 = 所属环境槽位路径；Conda 前缀依赖它，挂载时必须一致 |
| `hostBinding` | 创建时的 `{ user, homePath, arch, osVersion }`；不一致时拒绝或要求重新验证 |
| `lastVerification` | 最近一次 `VerificationRun` 的 id、结果、时间 |
| `mutatedSinceVerification` | 自上次验证后是否以受管理方式写挂载过 |

**身份核对**：挂载前同时比对 `image.json.imageId`、卷内 `.devstore/manifest.json` 的 `environmentId` 与 `imageId`、`volumeUUID`、存储库 `storeId`。任一不符即拒绝挂载并报告，不靠单一 UUID 判断。卷内清单记录 `imageId`，所以复制映像后必须先通过"导入副本"流程写入新 `imageId`，否则两个副本自称同一映像会被识别为冲突。

### 3.3 Checkpoint（检查点 / 归档）

不可变。用于升级前回滚点和停用归档，二者是同一实体，只是 `purpose` 不同。

| 字段 | 说明 |
|---|---|
| `checkpointId` | 随机 UUID |
| `environmentId`、`sourceImageId` | 来源 |
| `purpose` | `preUpdate` / `archive` / `manual` |
| `format` | `ULFO`（LZFSE，默认）/ `ULMO`（LZMA） |
| `encryption` | `none`（默认）/ `aes256`。活动可写映像默认不加密；只在生成归档或导出检查点时由用户选择加密。加密口令或钥匙串项引用不写入任何清单，恢复时需用户提供 |
| `fileBytes`、`sha256` | 如实验的 660,660,631 字节与 `61d8c5e2…` |
| `imageChecksumVerified` | `hdiutil verify` 结果；**不替代内容核对** |
| `contentManifestDigest` | 逐文件清单（路径、类型、模式、大小、内容摘要、链接目标）的摘要；实验恢复时核对 103,105 项 |
| `createdFrom` | 卸载状态下生成；记录生成时源映像的 `mutatedSinceVerification` |
| `verified` | 是否做过"恢复为临时可写卷 + 内容核对 + 运行验证"；只有为真的检查点才在 UI 中标为"已验证可恢复" |

### 3.4 Adapter（适配器声明）

适配器是**数据**，不是任意脚本：声明路径、环境变量、数据分类、宿主依赖与验证套件。实现上可以有少量内置代码（如 Conda 前缀修复），但必须由声明驱动并版本化。路径一律写成相对挂载点的 `${mount}/…`。

```json
{
  "id": "miniconda",
  "version": "0.1.0",
  "layout": {
    "sdkRoot": "${mount}/miniconda3",
    "state": "${mount}/state",
    "cache": "${mount}/cache",
    "tmp": "${mount}/tmp"
  },
  "sessionEnv": {
    "HOME": "${mount}/state/home",
    "PATH": "${sdkRoot}/bin:/usr/bin:/bin:/usr/sbin:/sbin",
    "CONDARC": "${mount}/state/condarc",
    "CONDA_ENVS_PATH": "${sdkRoot}/envs",
    "CONDA_PKGS_DIRS": "${sdkRoot}/pkgs",
    "PIP_CACHE_DIR": "${mount}/cache/pip",
    "XDG_CACHE_HOME": "${mount}/cache/xdg",
    "TMPDIR": "${mount}/tmp",
    "PYTHONNOUSERSITE": "1",
    "SSL_CERT_FILE": "${sdkRoot}/ssl/cert.pem",
    "OPENSSL_MODULES": "${sdkRoot}/lib/ossl-modules"
  },
  "originPathsToDeny": ["${home}/miniconda3", "${home}/.conda", "${home}/.condarc"],
  "dataClasses": [ "…见 3.5…" ],
  "hostDependencies": [ "…见 3.6…" ],
  "relocation": { "fixedPrefix": true, "method": "conda-pack@0.9.2" },
  "verificationSuite": { "id": "miniconda-core", "version": "1", "checks": 23 }
}
```

`sessionEnv` 取自实验脚本的实际映射；实验里的完整列表还有 Jupyter、Matplotlib、Torch 等目录，应原样纳入。会话变量**只注入 DevStore 启动的子进程**，不写全局 shell。

### 3.5 DataClass（卷内数据分类）

缓存不再是卷，而是带清理语义的路径分类。清理命令只接受分类 id，不接受任意路径。

| 分类 | 例（Miniconda） | 可清理 | 需备份 |
|---|---|---|---|
| `sdk` | `miniconda3/`（除下列子路径） | 否 | 是 |
| `envs` | `miniconda3/envs/*` | 仅按环境名经确认移除 | 是 |
| `state` | `state/`（condarc、HOME） | 否 | 是 |
| `cacheRebuildable` | `cache/pip`、`cache/xdg` | 是 | 否 |
| `cacheCostly` | `miniconda3/pkgs` | 需确认；清掉会影响离线安装 | 可选 |
| `tmp` | `tmp/` | 卸载前可清 | 否 |

每个分类记录 `paths`（可含排除）、`rebuildable`、`backup`、`sizeProbe`（统计方法）。卷用量 = 各分类之和 + 未分类，未分类部分在 UI 中如实显示，不归入缓存。

### 3.6 HostDependency（宿主依赖）

环境卷仍依赖宿主。适配器声明，挂载前由主机探测并记录结果。

| 字段 | 例 |
|---|---|
| `id` | `macos.arch`、`macos.version`、`xcode.clt`、`keychain.identity`、`network` |
| `requirement` | `arm64`；`>=15.0`；`optional` |
| `scope` | `always` / `forOperation`（如联网只在升级时需要） |
| `probe` | 内置探测器 id；结果写主机登记，不写卷 |

Miniconda 初版声明 `macos.arch = arm64`、`user/home = 创建时值`（因前缀固定）；`network` 仅 `update` 操作需要。

### 3.7 MountSlot 与 Lease

- **MountSlot**：以 `(kind, slot)` 为键，路径 `~/.local/dev/<kind>/<slot>`；同一 kind 可有多个槽位同时挂载。状态 `empty` / `mounted(imageId)` / `busy(transactionId)` / `stale`（底层目录非空或挂着未登记的卷）。
- **槽位归属**：槽位属于一个环境，在主机登记里记录 `slot → environmentId`。只有该环境的映像能挂到该槽位；同一环境不能同时挂在两个槽位。
- **槽位名固定**：前缀依赖路径（如 Conda），把映像换到另一个槽位等同于重新重定位，按"导入"流程处理并重新验证，不提供简单的重命名。槽位名限制为小写字母、数字、`-`、`.`，不能是 `.devstore` 等保留名。
- **多槽与会话**：同 kind 多实例同时挂载不会冲突，因为会话变量只注入子进程；`session` 操作必须指明 `environmentId`（或 kind+slot），不按 kind 猜测。
- **挂载点占位**：未挂载时该目录是空占位。任何写入前必须用 `statfs` 确认它是预期卷，而不是底层目录；占位目录出现内容时状态为 `stale`，拒绝挂载并报告。
- **Lease**：挂载时在存储库写 `lease.json`：`{ hostId, imageId, mountedAt, transactionId }`；正常卸载后删除。另一台主机看到租约即拒绝挂载。外置盘拔出或崩溃留下的陈旧租约只能由用户显式"接管"，接管前展示原主机与时间。
- **同 UUID 副本**：挂载前检查系统中是否已挂载同 `volumeUUID` 的卷；有则拒绝。

## 4. 生命周期

### 4.1 环境状态

```
draft ──导入/创建完成──▶ unverified ──验证通过──▶ ready ⇄ mounted
                            ▲                      │
                            └──受管理写入后─────────┘ (mutatedSinceVerification)
ready ──归档──▶ archived（仅检查点，无活动映像）──恢复──▶ unverified
任一 ──用户退役──▶ retired（文件不自动删除）
```

`mounted` 是 MountSlot 的状态投影，不单独存储。普通日常使用（运行 Python）不改变验证状态；`install`、`update`、`envs` 增删等受管理写操作会置 `mutatedSinceVerification = true`。

### 4.2 Operation：Plan → Grant → Transaction

所有写操作走同一管道：

1. **Plan**（只读，可由 Agent 发起）：解析目标、探测宿主、检查租约与空间，产出不可变计划：
   ```json
   {
     "planId": "…",
     "action": "restoreCheckpoint",
     "targets": { "environmentId": "…", "checkpointId": "…", "newImageId": "…(预分配)" },
     "preconditions": ["checkpoint.sha256 == 61d8…", "slot.miniconda == empty", "freeBytes >= 2.6e9"],
     "effects": ["创建 <store>/environments/miniconda/<env>/<new>.sparsebundle", "挂载到 ~/.local/dev/miniconda/current"],
     "notTouched": ["~/miniconda3", "~/.zshrc"],
     "requiresNetwork": false,
     "planDigest": "sha256:…"
   }
   ```
2. **Grant**（只能由用户产生）：绑定 `planDigest`、发起者、有效期（默认数分钟）、一次性。来源只能是 GUI 确认、CLI 的交互式 TTY 确认，或用户预先配置的策略。**MCP 调用里的任何 `confirmed: true` 字段都不构成授权**。
3. **Transaction**：执行前重新检查前置条件；任一不符即作废授权并要求重新 plan。每步写入主机事务日志（`started`/`stepDone`/`committed`/`rolledBack`/`abandoned`）。中断后启动时扫描日志，只做"安全回退"（卸载、删除本次新建且未登记的映像），其余交给用户。

### 4.3 能力分级

| 级别 | 操作 | Agent 经 MCP |
|---|---|---|
| `inspect` | 列表、状态、用量、验证记录、宿主探测 | 直接允许 |
| `plan` | 任何操作的预演 | 直接允许 |
| `session` | 在已挂载且 `ready` 的环境中运行登记的入口命令 | 按用户策略；不等于隔离 |
| `mount` | 挂载、卸载 | 需授权；可为单个环境开启常驻策略，默认关闭 |
| `mutate` | 安装/升级、清理分类、建检查点、恢复、切换、转移、compact | 每次授权 |
| `destructive` | 删除映像或检查点、接管陈旧租约、导入秘密、迁移原安装 | 每次授权，且只能在 GUI/TTY 确认，不接受策略 |

`session` 级运行的构建脚本可能访问宿主，计划和 UI 里需明确写出这一点。

**常驻策略**只允许用于 `mount` 级，按环境逐个开启（不能按 kind 或全局开启），默认关闭。策略本身只能在 GUI/TTY 中创建或撤销，写入 `grants.jsonl`，绑定 `environmentId` 与允许的动作（`mount`/`unmount`）。策略下的每次挂载仍走 Plan 与前置条件检查，只是免去逐次确认；`mutate`、`destructive` 永远逐次确认。

### 4.4 关键流程要点

- **导入**：新建映像 → 固定路径挂载 → 适配器重定位 → 写卷内清单 → 卸载重挂 → 验证 → `ready`。原安装只读，结束时比对原安装清单（实验的 103,075 项做法）。
- **升级**：卸载 → 建 `preUpdate` 检查点 → 挂载 → 更新 → 重新发现组件 → 验证。失败：把检查点恢复为新映像（`standby`）→ 验证 → 切换；失败的映像标 `retired`，不删除。
- **转移**：只复制已卸载映像 → 新 `imageId` → 在目标挂回同一固定路径 → 验证 → 新映像成为 `active`，旧映像 `retired`。`hostBinding` 不符时先拒绝，提示需要另做前缀验证。
- **跨存储库**：同一环境的映像可以分属内置盘和外置 SSD 等不同存储库（转移即是此场景），但 `active` 只有一个，切换 `active` 是 `mutate` 操作。UI 按环境分组列出全部映像，并标出所在存储库、角色和存储库是否在线；离线存储库中的映像只显示登记信息，不可挂载。
- **归档/恢复**：同 3.3；恢复后的映像必须经内容核对和运行验证才能切换为 `active`。
- **空间检查**：恢复/转移计划须计入原本、归档、新映像三份空间，不自动删除任何一份腾空间。

## 5. 验证证据

验证是一等数据，UI 和 Agent 读取它判断"能不能用"，而不是读日志。

```json
{
  "runId": "…",
  "target": { "imageId": "…" },
  "phase": "remounted",
  "suite": { "id": "miniconda-core", "version": "1" },
  "adapterVersion": "0.1.0",
  "host": { "arch": "arm64", "os": "15.7.9", "storeMedium": "internal" },
  "confinement": { "deniedPaths": ["~/miniconda3", "~/.conda", "/opt/homebrew", "/usr/local"], "network": "denied" },
  "negativeControlPassed": true,
  "checks": [{ "name": "python3.10.numpy_torch_cpu", "passed": true, "seconds": 4.2 }],
  "summary": { "passed": 23, "total": 23 },
  "coverage": {
    "covered": ["Python/pip", "conda CLI 与插件", "离线建环境", "NumPy/PyTorch CPU"],
    "notCovered": ["GPU/MPS", "GUI Python", "在线升级", "外置 SSD", "跨 Mac", "compact"]
  }
}
```

规则：

- **负向对照未通过则整轮无效**，不计入通过数。
- 失败轮次保留，不覆盖（实验中首次 python3.10 三项失败的记录即属此类）。
- `coverage.notCovered` 必填；UI 显示"已验证范围"，不显示笼统的"可用"。
- 输出截断后的 stdout/stderr 单独存放，记录只保留摘要与引用。


现有三个实验映像不是按本模型创建的，没有卷内清单和 `imageId`。实现后若要纳入，走"导入副本"流程逐个登记，且一次只挂一个。

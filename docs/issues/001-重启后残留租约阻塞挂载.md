# 001 重启后残留租约阻塞挂载

- 状态：已修复（2026-11-06）
- 发现：2026-11-05
- 影响：所有环境（`mount`、`compact`、`archive`、`delete` 均被阻塞；终端启动时的自动挂载也失败）
- 组件：DevStoreCore（`Operations.swift`、`Operations+Archive.swift`、`Operations+Lifecycle.swift`）

## 现象

```
$ devstore mount rust/current
Error: preconditions not met:
  ✗ no lease on the image (not mounted by any host)
```

MCP `devstore_plan_mount` 返回同样的错误。`devstore status` 显示 `unmounted`，但 `devstore_status` 的 JSON 中六个环境都带 `lease`（`mountedAt` 2026-11-02T17:10，`hostId` 为本机 `39014920-…`）。新终端只打印 `devstore: rust/current 未挂载（devstore mount rust/current）`。

## 原因

1. 2026-11-02 17:10 六个环境被挂载，`executeMount` 写入 `images/<imageId>/lease.json`。
2. 本机在 2026-11-05 03:06 重启（`kern.boottime`），卷随之被系统卸载，没有经过 `executeUnmount`，`lease.json` 留在存储库中。
3. `mountChecks` 仅以 `lease.json` 是否存在判断 `!leaseExists`，不区分租约属于本机还是别的主机，也不判断该卷是否仍挂着。因此残留租约永久阻塞挂载，并且 CLI/MCP 都没有清理途径。

`archiveChecks`（`image holds no lease`）、`deleteChecks`（`no image of the environment holds a lease`）以及依赖“已卸载”前提的 `compact` 有同样问题。

## 提示文案问题

`✗ no lease on the image (not mounted by any host)` 读起来像“缺少租约”，实际含义是“存在租约”。失败时应该写清楚实际状态，例如：

```
✗ image holds a lease from host 39014920-… (this host) since 2026-11-02T17:10:15+08:00, but no volume with UUID 9321F3C7-… is mounted — stale lease (host rebooted?)
```

## 临时处理（2026-11-05 已执行）

确认 `hdiutil info` 中没有对应映像、六份租约的 `hostId` 均为本机且早于开机时间后，把六个 `lease.json` 移出存储库备份（未删除），随后 `devstore mount rust/current`、`android/current` 成功。备份位于当时会话的临时目录，不在 SDK 卷内。

## 修复建议

- **自动回收本机残留租约**：同时满足以下条件时视为残留，`mount`（及 `compact`/`archive`/`delete` 的检查）记日志后回收，并在计划的 `effects` 里写明“回收残留租约”：
  - `lease.hostId == registry.hostId`；
  - `DiskImage.mountedImageVolumeUUIDs()` 中没有该卷 UUID，且 `slotPath` 不是挂载点；
  - （可选加强）`lease.mountedAt` 早于 `kern.boottime`。
- **他机租约不自动回收**：`hostId` 不同时保持阻塞，并在提示中给出主机 id 和时间；如需手工回收，提供 `devstore lease clear <env>` 这类需交互式终端批准的计划（`level` 与 `delete` 同级或单独一级），不要让 Agent 直接删文件。
- `status` / `devstore_status` 增加 `leaseStale: true` 或在文本输出中标注“残留租约”，使用户和 Agent 一眼看出。
- 终端 shell 块自动挂载失败时，把 `mount` 的实际错误打印出来，而不只是提示“未挂载”。
- 日志：回收时写一条 `journal` 记录（`step lease-reclaimed`，含原租约的 `transactionId`）。

## 验收

- 单元测试：本机残留租约（无挂载卷）→ 挂载计划通过并回收；本机租约且卷仍挂载 → 阻塞；他机租约 → 阻塞并给出主机信息。
- 实机：挂载后重启（或 `hdiutil detach` 绕过 DevStore），再 `devstore mount` 成功；`journal` 有回收记录。
- 错误文案在 CLI、MCP、桌面应用三处一致。

## 修复（2026-11-06）

- `DevStoreCore/LeaseAssessment.swift`：`LeaseAssessment.assess` 把租约分为 `none` / `active` / `pending` / `stale` / `foreign`。本机租约在卷 UUID 未挂载、槽位不是挂载点时，若早于 `kern.boottime`、其挂载事务在日志里已结束、或超过 10 分钟，判为 `stale`；未结束且不到 10 分钟判为 `pending`（防止两个终端同时启动时互相回收）。
- `mount`、`compact`、`archive`、`delete`：残留租约不再阻塞；计划效果写明 `reclaim stale lease …`，执行时删除并记 `step lease-reclaimed`（detail 含原事务号与原因）。他机、使用中、挂载中的租约仍阻塞，失败文案即该状态原文（主机 id、时间、卷 UUID、处理办法）。
- 新增 `clear-lease` 计划（`devstore lease clear <env>`、MCP `devstore_plan_clear_lease`、应用租约卡片的“清除租约…”），级别 `destructive`，任何策略都不覆盖；计划绑定当时那份租约的事务号，执行记 `step lease-cleared`。
- `status` / `devstore_status` 增加 `leaseState`、`leaseSummary`；CLI 文本输出标出 `lease=stale` 等并给出原文；应用侧栏、卡片、详情、菜单栏同步显示。
- `~/.zshenv`（rust）与 `~/.zshrc`（miniconda、flutter、dotnet、android、go）的 DevStore 块改为保存 `mount` 的标准错误，未挂载时打印出来（备份 `*.devstore-backup-20261106-230848`）。

验收：

- 单元测试 `LeaseTests`：状态分类；本机残留租约 → 挂载计划通过，执行时先回收并记日志；他机租约 → `mount`/`compact`/`delete` 均阻塞并给出主机 id 与 `devstore lease clear`，清除计划为破坏性且策略不覆盖；挂载中的本机租约 → 阻塞；删除时回收残留租约。
- 实机（`DEVSTORE_INTEGRATION=1`，临时卷）：挂载 → `hdiutil detach` 绕过 DevStore → `status` 为 `stale`（“volume detached outside DevStore”）→ 再挂载成功，日志有带原事务号的 `lease-reclaimed`。
- 日常环境：2026-11-06 21:52 重启后 `rust/current`、`miniconda/current` 再次留下租约；安装新版后打开新终端，两者自动挂载，日志记录了两条 `lease-reclaimed`（原事务 `3c3ca558…`、`71da1871…`）。

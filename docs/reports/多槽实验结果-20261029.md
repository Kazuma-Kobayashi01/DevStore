# 多槽实验结果

日期：2026-10-29。方案：[实验方案 B](../design/实验方案-compact与多槽.md)。结论：**用 conda-pack 把 Miniconda 实例重定位到第二个槽位 `~/.local/dev/miniconda/lab` 后，在禁止读取 `current` 槽位和原安装的条件下通过 23 项验证；两槽同时挂载时，各自禁止读取对方，单独运行和并发运行都通过；卸载一个槽位不影响另一个槽位上正在运行的任务。** 共 7 轮，166 项全部通过。

另有一项**新发现**：两个槽位里都还有 703 个二进制文件和 7,784 个 `.pyc` 文件含有原安装的路径 `/Users/jackson-hao/miniconda3`。这是昨天的实验映像就已存在的问题，旧报告没有提到（见"前缀残留"一节）。

|---|---|---|---|
| `current` | `artifacts/experiments/multislot-20261029/current-src.sparsebundle` | `91FF58B2-…` | `miniconda.sparsebundle` 的 APFS 克隆 |

新建了占位目录 `~/.local/dev/miniconda/lab`。原 `~/miniconda3` 不作为重定位来源。

## 重定位（B2）

- `current` 只读挂载，用它自己的 base Python 在沙箱中运行 conda-pack 0.9.2。沙箱禁读原安装、`~/.conda`、`~/.condarc`、Homebrew 和 `/usr/local`，禁网，只允许写 staging 目录；先确认负向对照有效。
- conda-pack 代码来自旧实验从同一 wheel 解出的 `tool/` 目录。wheel 的 SHA-256 与 PyPI 记录一致，`tool/` 的 26 个文件与 wheel 逐一比对一致。第一次直接从 `.whl` 导入时，conda-pack 读不到 zip 内的激活脚本，打包失败，于是删除了那次的部分产物，改用 `tool/` 重跑。
- 处理方式与昨天一致：base 的 `python.app` 按 post-link 后的实际布局加入 8 个条目，并忽略记录中已不存在的 `pythonapp` 路径；所有环境都以 tar 格式打包并解包，不使用 no-archive。
- 解包核对：base 共 18,048 个唯一路径，llama-cpp 9,280 个，neocloud 11,266 个，python3.10 53,452 个，**缺失 0**。
- `pkgs/` 用 `ditto` 从 `current` 复制；`state/condarc` 中的路径由 `current` 替换为 `lab`；`state/home`、`cache/`、`tmp/` 新建，没有复制 `current` 的 HOME 内容。
- `miniconda3/` 下两槽的路径集合完全一致（各 103,093 项），其中 400 个文件因前缀重写而内容不同。`pkgs/cache` 目录的 setgid 位在 `ditto` 复制时丢失，已手动补回 `2775`。

## 前缀残留（B3）

| 扫描 | 结果 |
|---|---|
| lab 中的 `/.local/dev/miniconda/current` | 2 个文本文件，都是包缓存记录（`pkgs/urls.txt` 和验证探针包的 `repodata_record.json`）；可执行脚本、shebang 和二进制中都没有 |
| lab 中的 `/Users/jackson-hao/miniconda3` | 703 个二进制、7,784 个 `.pyc`、3 个 `conda-meta/history` |
| current 中的 `/Users/jackson-hao/miniconda3`（对照） | 与 lab 相同，另多 1 个文本文件（`experiment.json`，实验说明） |

原安装路径的残留在昨天制作 `current` 时就已存在。原因是源包缓存已被清理，conda-pack 把这些包当作非受管文件处理：文本文件做了前缀替换，但在 macOS 上不改写二进制文件。残留主要在 gettext 工具、`xmllint` 和部分 dylib 中，通常是编译进去的默认配置或数据目录路径；`.pyc` 中的残留是源文件路径，只影响回溯信息。

这些路径都没有被 23 项验证用到。原安装被禁读时验证仍然通过，说明测到的能力不依赖它们。但如果某个工具运行时会读取编译进去的路径，在原安装被移走以后，可能会**静默回退或失败**。这扩大了昨天报告中"源包缓存缺失、前缀重写不完整"那条警告的实际范围。

## 验证

| 轮次 | 条件 | 结果 |
|---|---|---|
| B4 `lab-alone` | 只挂 lab；额外禁读 `current` 路径 | 23/23 |
| B6 `both-current` / `both-lab` | 两槽同时挂载（current 改为可写）；各自禁读对方，并多一项跨槽负向对照 | 24/24，24/24 |
| B7 并发 | 两槽同时运行完整套件，包括离线建环境、安装本地包、删除环境、NumPy/PyTorch 计算 | 24/24，24/24；约 19 秒，两边耗时几乎相同，探针包各自落在本卷的 `pkgs/` |
| B8 | lab 上运行 25 秒的 PyTorch 计算，开始 5 秒后卸载 current | 卸载成功，lab 任务正常结束（65,908 次迭代，结果有限）；之后 lab 23/23，current 重挂后 24/24 |
| B9 对照 | 把 lab 映像只读挂到 `current` 路径 | Python、pip、NumPy/PyTorch 能运行（Python 可以按自身位置定位前缀）；`conda` 因 shebang 指向 `lab/.../python` 报 `bad interpreter` 而失败 |
| B10 | 实验结束后再次只读挂载 current-src，与 B1 的清单比对 | 103,111 项净变化为 0 |

B9 说明，把映像挂到错误的槽位并不会全面失败，而是"看起来大部分能用、conda 坏了"，比直接报错更危险。这支持数据模型中"挂载时必须比对 `fixedMountPath`"的规则，不应放宽。（`B9-slot-swap-control.txt` 中的 `exit=0` 是 `tail` 的退出码，文件末尾已注明。）

## 对设计的结论

按方案判定规则，属于"B4、B6 全通过，B3 残留不在可执行路径"：

1. 多槽可行。同一 kind 的两个实例可以同时挂载、同时写入，互不借用。会话变量只注入子进程的做法已足够，没有发现需要额外隔离的路径。
2. "换槽位 = 按导入流程重新重定位"成立。整个过程（打包约 16 秒，加上解包和核对）可以由适配器自动完成，产物需要重新验证。
3. Miniconda 适配器的导入步骤应增加**前缀残留扫描**，同时扫描原安装路径和旧槽位路径，按 shebang/文本/二进制/pyc 分类报告。可执行文本中出现残留时应阻止登记；二进制中的残留作为已知警告写入环境清单。
4. 复制 `pkgs/` 时需要保留 setgid 等特殊权限位，导入后按内容清单核对模式。
5. 挂载时必须核对 `fixedMountPath`（B9）。

## 未覆盖与局限

- 只测了两个槽位，都在内置盘、同一用户、同一台 Mac 上。
- 703 个二进制中的残留路径具体在什么时候会被读取，没有逐个分析，也没有在原安装被移走的情况下做测试（这需要动原安装，不在本次授权范围内）。
- 并发只测了一次约 19 秒的运行，不是压力测试。
- GUI Python、GPU/MPS、在线升级、外置 SSD 同样未测。

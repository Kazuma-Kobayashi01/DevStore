# 可写独立环境挂载与压缩方案 v2

> 此稿已由 [单卷独立环境挂载方案 v3](单卷独立环境挂载方案-v3.md) 替代。Miniconda 单卷实验通过后，默认改为每个环境一个可写卷，缓存与状态在卷内管理；本文件仅保留设计历史。

日期：2026-10-29。状态：规划稿。替代 v1 的 SDK 只读方案；本轮仅修改文档，没有创建映像、下载 SDK、改动现有安装或执行迁移。

## 1. 核心决定

取消 SDK 只读限制。运行中的环境卷和缓存卷均使用**可写 APFS sparse bundle**，以最大程度减少对原安装、本机默认用户目录和全局包管理器的依赖为目标。

两卷的职责改为：

| 卷 | 内容 | 保存与清理规则 |
|---|---|---|
| 环境卷 | SDK/runtime、工具管理器、必要的自带依赖、用户安装工具、配置和持久运行状态 | 是需要备份和回滚的主体；不能按缓存清理 |
| 缓存卷 | 能可靠独立定位、允许丢弃并重建的下载缓存、构建缓存和临时数据 | 可独立挂载、归档及按明确规则清理；不是所有缓存都必须从环境卷拆出 |

**独立性优先于强制拆分缓存。** 对混合了缓存、配置、安装记录和锁的工具目录，先整体放入环境卷并保留工具原生结构；只有适配和测试证明安全后，才将其中纯缓存外置。不靠大批跨卷符号链接拼凑运行目录。

SDK 内部的缓存、锁、版本文件和更新写入均允许存在，因此 Flutter 不再因这类写入而被排除。环境升级、组件安装和用户工具安装可在受管理卷中完成；升级前生成可恢复检查点，执行和联网范围由具体操作计划说明，不自动动原安装。

## 2. 挂载和存储布局

| 位置 | 含义 |
|---|---|
| `~/.local/dev/<kind>/current` | 当前环境卷的真实挂载点，可写 |
| `~/.local/dev/<kind>/cache` | 可选独立缓存卷的真实挂载点，可写 |
| `<存储库>/environments/<kind>/<environment-id>/environment.sparsebundle` | 活动环境映像；存储库可在内置盘或外置 SSD |
| `<存储库>/caches/<kind>/<cache-id>/cache.sparsebundle` | 外置的纯缓存；默认由一个环境/主机使用 |
| `<存储库>/checkpoints/<environment-id>/<checkpoint-id>.dmg` | 卸载后生成的压缩检查点或归档 |
| 本机 `~/.local/state/dev-environments` | 主机登记、操作日志和存储库定位；可由导入包重建，不作为环境运行所需配置的唯一存放处 |

环境卷的根是环境工作区，约定包含 `sdk`、`state`、`tools`、`deps` 和环境清单。各 SDK 的官方目录结构完整保存在 `sdk` 内；工具实际根路径由适配器映射，而不是假设环境卷根就是 SDK 根。例如 Go 的根为 `current/sdk`，其可执行文件为 `current/sdk/bin/go`。

`state` 保存用户级配置和工具状态，`tools` 保存持久用户工具，`deps` 保存可用户级打包的附属运行时，例如独立 JDK。配置优先按环境根计算相对位置，保存登记时不固化外置盘卷名或原 Mac 用户名。`current` 与 `cache` 是同级实际挂载点；不嵌套挂载、不把 `current` 同时用作版本链接。v2 每类环境同一时间只有一个活动实例，多实例并行以后另做路径约定。

活动环境可变，环境 ID 不等同于 SDK 版本或文件内容摘要。每个已验证检查点单独记录当时的 SDK/组件版本、内容摘要和依赖；后续升级不能继续冒充旧版本检查点。清单、配置和持久状态在环境卷中；映像旁的导入清单与摘要是便于发现和恢复的副本。

## 3. 各环境的独立化策略

| 环境 | 环境卷内保存 | 第二卷与关键限制 |
|---|---|---|
| Go | 完整 SDK；环境专属 GOPATH 状态；GOBIN 指向持久工具目录 | `GOCACHE`、`GOMODCACHE` 可映射缓存卷；初始固定 `GOTOOLCHAIN=local`，其他工具链由明确安装操作加入并记录，避免隐式使用原安装 |
| .NET | 官方独立二进制 SDK、所需 runtime/packs、`DOTNET_CLI_HOME`、持久工具与组件状态 | `NUGET_PACKAGES` 可指向缓存卷；从官方 arm64 归档建立新实例，不依赖当前 root 所有的安装。workload/工具安装不因只读被禁止，但每项需验证其写入和宿主依赖 |
| Rust | 完整独立 `RUSTUP_HOME` 放在 `sdk`；完整独立 `CARGO_HOME` 放在 `state/cargo`，含 rustup、代理、安装工具与锁 | 不把 Cargo Home 当成可删除缓存；初期整体保留，允许原生 rustup/toolchain 管理。项目 `target` 等只有在路径、并发和生命周期验证后才外置；源码和重要产物不默认视作缓存 |
| Flutter/Dart | 完整 Flutter 工作树及原生 `bin/cache`；环境内 Pub/工具状态和 Dart 工具安装数据 | 初期 Pub 状态整体留环境卷，避免丢失全局工具激活记录；可安全外置的构建临时数据再放第二卷。Flutter 的原生写入、预缓存与升级允许，但升级须有检查点 |
| Android | 完整 SDK/NDK、环境专属 Android 用户目录、AVD 状态、Gradle User Home；兼容的独立 JDK 放入 `deps` | Gradle User Home 混合配置、wrapper、daemon 和缓存，初期完整留环境卷；不默认整体标为可丢弃缓存。允许 sdkmanager 管理环境内组件，逐项校验 JDK、许可证和项目路径 |
| Node.js / 独立 JDK | 未来可用官方独立包建立；全局工具和持久状态随环境 | 去除只读限制后可纳入同一模型，但尚未扫描或完成验收，不能标记已支持 |
| Python 等 | 需要可搬运发行物及专门适配 | 可写解决不了解释器、venv、shebang 或动态库中的绝对路径，不直接复制系统 Python 或现有 venv 并宣称独立 |

Rust 原生支持指定 `RUSTUP_HOME` 与 `CARGO_HOME`，因此可先用完整用户级结构实现独立实例，无需为只读牺牲 rustup 管理能力。[rustup 安装说明](https://rust-lang.github.io/rustup/installation/)、[环境变量](https://rust-lang.github.io/rustup/environment-variables.html)。

Android 使用环境内的 `ANDROID_HOME`、`ANDROID_USER_HOME`、`ANDROID_AVD_HOME` 和 `JAVA_HOME`；Gradle User Home 用 `GRADLE_USER_HOME` 定位。已有 AVD 与项目可能包含绝对路径，导入后必须复核，不能仅靠修改变量宣称完成迁移。[Android 环境变量](https://developer.android.com/tools/variables/)、[Gradle 目录说明](https://docs.gradle.org/current/userguide/directory_layout.html)。

.NET 的 CLI 支持状态和全局工具不是纯缓存，随环境保存；只将独立定位的 NuGet 包缓存放到第二卷。Dart 的包目录也可能承载已激活的用户工具，因此不能按缓存卷整体丢弃。[Microsoft 环境变量](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-environment-variables)、[Dart 用户工具说明](https://dart.dev/tools/pub/cmd/pub-global)。

环境卷仅保存已选择的组件，不能承诺任意项目都离线可构建。项目源码、依赖清单、签名资产和外部服务配置仍需明确选择；所需包没有预缓存时，必须报告下载需求。

## 4. 独立性的验收边界

目标是尽量形成“复制环境映像后，在受支持的 Mac 上挂回固定路径即可用”的实例，同时逐项说明仍依赖什么：

- SDK、用户工具、配置和可用户级打包的依赖尽量随环境保存，使用启动会话的环境变量定位，不依赖原 Homebrew、root 安装或原用户默认目录。
- 内部链接和登记使用可重建路径；检查可执行入口、动态库、脚本 shebang、生成的工具启动器、项目配置及 AVD 引用。跨用户名、架构或系统版本转移必须复验，必要时重新生成启动器或重建相关状态。
- macOS 内核与系统框架仍是宿主依赖；Xcode、模拟器虚拟化能力、系统权限、钥匙串身份和系统服务不能保证随普通 SDK 映像独立搬走。Flutter iOS/.NET Apple workloads 等所需 Xcode 明确列为宿主前置条件。
- 在清理过的子进程环境中执行，明确选择卷内 SDK、配置和附属依赖；检查旧路径引用及实际解析路径。若无法阻断或观察原安装路径的访问，则独立性只记为部分验证，不记为已证明无外部依赖。
- 用户秘密默认由本机安全存储提供，不自动导入原有凭据。需要随环境搬运的 ADB/签名等密钥须明确选择，并使用加密私有环境及备份；可分享导出排除秘密。宿主安全身份可以成为明确、可重新配置的外部依赖。

独立性分三层记录：同一 Mac 跨盘转移、同架构/兼容系统的其他 Mac、不同架构/系统；前一层通过不代表后一层通过。仅把镜像搬到另一目录不能代替实际外置盘或跨 Mac 测试。

## 5. 缓存可选，但不能静默丢失状态

只有适配器认定可重建的数据才进入缓存卷。SDK 内部原生缓存和混合目录可以留在环境卷，优先保证可运行、可备份和可转移；后续优化空间不改变数据保留语义。

若某个操作声明需要缓存卷，未挂载时明确失败；可通过单独操作创建全新空缓存或显式选择环境内缓存模式，不能悄悄写入挂载点底层目录。切换缓存模式和路径会登记到环境清单；不会自动清理旧数据。只有声明无需第二卷的环境和操作，才允许只挂环境卷运行。

缓存卷可以选择一起搬走以改善离线和热启动；也可在目标机新建，并通过明确的依赖恢复流程重建。清空缓存会影响离线能力，不能保证网络不可用时仍可重建。包含用户工具、凭据或唯一源码的目录不得被“清空缓存”覆盖。

## 6. 压缩改为停用后的归档能力

| 操作 | 运行时/维护方式 |
|---|---|
| 日常使用 | 环境卷和缓存卷都使用 APFS 可写 sparse bundle |
| 空闲空间回收 | 正常卸载后对临时副本 compact，验证后再登记；只回收未使用的带区，可能没有收益 |
| 压缩归档/检查点 | 正常卸载后转成 LZFSE（默认 ULFO）或 LZMA（可选 ULMO）压缩 DMG |
| 从压缩包启用 | 还原为新的可写 sparse bundle，校验后再挂载使用，不让活动环境被压缩归档格式的只读特性限制 |

压缩 DMG 本身是只读存储格式，但在本方案中仅用于停用归档和检查点，不是运行模式。v2 不使用压缩基底加 shadow 的日常组合，避免环境依赖多个隐含文件。也不承诺 APFS 可写卷具有全卷实时压缩。[Apple 映像格式说明](https://support.apple.com/guide/disk-utility/convert-a-disk-image-to-another-format-dskutl1002/mac)。

压缩率、恢复空间和速度以实验为准；已有压缩包可能几乎不再缩小。记录原本、归档、临时副本和恢复卷的实际占用，不能仅凭虚拟容量推算所需空间。已加密的环境在压缩和恢复时必须保持加密策略，不把秘密写到未加密中间产物；密钥不进入日志或命令行参数。

转换、回收、备份和转移都在任务停止且卷正常卸载之后进行。先保留可恢复原本，操作临时目标，验证内容、元数据和挂载运行结果后才切换登记。可写映像没有与只读压缩 DMG 相同的内置校验和保证，使用文件清单、内容摘要和恢复测试；原本不因转换成功就自动删除。

## 7. 更新、挂载与回滚

可写允许工具在环境内正常写入；管理员的升级操作仍须明确目标和联网范围。升级默认流程：停止使用 → 正常卸载并建立检查点 → 挂载原环境或新工作副本 → 执行明确更新 → 重新发现实际版本/组件 → 验收 → 更新清单。工具原生更新会影响哪些目录由适配器记录；更新失败时保留失败实例和诊断，恢复检查点为另一个可写实例再切换。

缓存不保证与检查点同步可恢复，环境内的持久状态必须随环境一起备份；若某工具要求两卷一致，备份计划同时冻结并登记两卷。默认不靠内部 APFS 快照替代独立备份；同一 SSD 上的两个副本也不算独立物理备份。

挂载前核对真实路径、所有者、空目录、磁盘与映像身份；复制映像可能保留卷 UUID，不能只靠 UUID。当前设备、映像实际路径和登记的环境/检查点身份共同确认。两卷都可写，同一逻辑实例默认只允许一台主机使用；不在实时同步盘中并发打开。

通过会话设置 PATH 与工具变量；不自动改全局 shell、系统链接、原包管理器或 IDE。缺组件时报告，不静默用原安装填补。配置 GUI/IDE、安装组件和升级是单独可审阅操作。卸载先关闭相关任务、daemon 和模拟器；卷忙则停止，不强制卸载。恢复或跨盘切换前再次检查权限、架构、宿主依赖和固定路径。

## 8. CLI、MCP、GUI 的设计调整

核心模块仍为发现、适配器、计划、映像管理、会话和验证；环境规格改为包含 SDK、工具管理器、持久状态、可选缓存及附属依赖。活动环境身份与不可变检查点身份分开；运行写入、组件变更和升级不能继续引用旧内容摘要冒充未变化。

公共能力收敛为：检查与预览、挂载环境/缓存、启动会话、检查点、更新组件、回滚、回收空间、归档、恢复、跨盘转移。原来“压缩 SDK 后直接运行”的默认行为改为“归档环境/缓存，恢复成可写实例后使用”。原来因 SDK 只读而禁用的 rustup、Flutter、sdkmanager 管理操作进入各自适配计划；尚未验证的不标记已支持。

界面明确区分“环境数据，需要保存”和“可重建缓存”；清理只作用于明确列出的缓存类别。确认绑定计划、环境、卷、路径及影响；Agent 自报确认不等于用户授权。所有操作只作用于受管理实例，旧环境迁移仍需先出示具体复制和切换计划。用户当前只要求规划，不执行安装或迁移。

## 9. 实验顺序与验收

1. Go 仍为首个实验：内置盘，独立副本，创建可写环境卷与空缓存卷；验证卷内 SDK、工作区/用户工具路径、冷/热编译、缓存缺失行为和正常卸载重挂。使用 SDK 自带测试文件，不编写管理器应用代码。
2. 验证环境内持久状态的写入和重挂保留；将独立缓存替换为空卷，确认用户配置和持久工具没有丢失。独立缓存仍需的依赖明确报告，不假定离线可重建。
3. 验证环境检查点、缓存 compact、压缩归档与恢复为可写卷；恢复后比较内容和必要元数据，重复编译，并验证原实例与恢复实例互不改写。
4. 接入外置 SSD 后复验跨盘运行；然后测试官方独立二进制 .NET，验证 CLI 状态随环境保留、NuGet 缓存可分离以及原 root 安装不变。
5. Flutter、Rust、Android 重新进入后续适配范围：分别验证原生更新写入、工具安装状态、混合目录完整性、附属 JDK、AVD 和实际项目使用；不再以只读兼容性作为淘汰条件。

统一停止条件：路径/卷身份错误、权限不符、空间不足、无法恢复、写入原安装、未声明的宿主依赖、秘密意外外泄、校验不一致、卷忙或断连。每项独立化结果有证据与未知项，不用“最大独立化”表述替代可验证的兼容性结论。
